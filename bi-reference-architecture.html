Two places, one decision. The SCD type is chosen and implemented in Transform: the load job compares the incoming attribute against the version already stored and decides whether to overwrite it, close it and open a new row, or move it into a previous-value column. The result is materialised in the Core data warehouse, which is the only layer that keeps history at all. Everything above it — marts, cubes, dashboards — simply inherits whatever the core decided. That is why a Type 1 mistake cannot be repaired in the frontend: by the time the report is built, Ringstraße no longer exists anywhere.
One question, three answers: where do the aggregates live? The star schema in the evaluation database is the relational answer — ROLAP computes every sum with SQL the moment it is asked, so figures are always current and volume is limited only by the database. The OLAP cube is the multidimensional answer — MOLAP copies facts and pre-computed aggregates into its own store: fastest to read, but only as fresh as the last processing run. HOLAP sits on the link between them: the pre-computed levels stay in the cube, the detail stays relational, and the engine routes each query to whichever layer can answer it. Note what stays dark: the whole decision lives in the output layer. Sofia can switch storage mode without touching a single row in the core warehouse.
